ログインの全体フロー
①ブラウザーログインして→認証サービス（本人確認の専門家）
②ブラウザ←証明書（Token）ー認証サービス
③ブラウザーAPIを呼ぶ＋証明書→バックエンド
④バックエンドー証明書は本物？→認証サービス
⑤バックエンド←証明書は本物ですー認証サービス
⑥バックエンド←本物です。このユーザーのIDはabcです。ー認証サービス
⑦バックエンドーabcさんのフォローを取り出す→DB

決定事項
①誰が確認するか
→SupabaseAuthで実現する
②ログインの手段
→Google ログイン。一通りのログイン機能を作成後に、メール＋PWも実装する。
③作る範囲
→ログイン・ログアウトのみ作成する。
④ログインしていない人への見せ方
→ームと推し詳細は誰でも見られる。ログインすると「フォロー中の推し」が増える、という形。「ダッシュボード」タブは見れなくする。
⑤保存するデータ
→ユーザー情報は Supabase が管理します。自分で作るのは「誰が誰をフォローしているか」のテーブルだけです。
⑥APIの形
→ユーザー ID は URL ではなく、証明書から取り出す
⑦見本のユーザーはどうするか
→削除する。ログインしていないと見えない情報は隠す。ただし、現在はAIチャットがdemo_users テーブルを読んでいるので実装は待つ。

現場で重ねる6つの網
変更の前から本番に出たあとまで、順番に並べます。

#	タイミング	網	何を見つけられるか
1	変更前	影響範囲の調査（検索）	消す・変えるものを使っている場所
2	変更前	持ち主に聞く	コードからは読み取れない意図や予定
3	書いている最中	型チェック・ビルド	名前の変更や消し忘れによる食い違い
4	マージ前	自動テスト ＋ CI	動かすと壊れること
5	マージ前	コードレビュー（PR）	持ち主だから気づける影響
6	本番に出たあと	ログ・監視	すり抜けて本番で起きたエラー
1. 影響範囲の調査
消したり変えたりする名前で検索します。

テーブル名・API の URL・環境変数名: Ctrl + Shift + F の文字列検索。supabase/migrations/ の SQL も対象に入れます。
関数名・型名: 関数名の上で右クリックして「すべての参照を検索」（Shift + F12）を使うと、その関数を呼んでいる場所が一覧で出ます。
2. 持ち主に聞く
検索で使っている場所が見つかったら、誰が・なぜ作ったかを調べて相談します。


git log -S "demo_users" --oneline
これで、demo_users という文字を追加・削除したコミットと、その作者がわかります。VS Code では、行の横に作者を表示する機能（git blame）でも確認できます。

コードを見るだけでは、「来週このテーブルを使う機能を足す予定」のような頭の中にある予定まではわかりません。なので、login.md のような設計メモを実装の前にチームへ見せるのが、いちばん安上がりな網になります。

3. 型チェック・ビルド
TypeScript では、使われている名前を消すと、保存した時点で使っている側が赤線になります。前に話した「型の約束」が網として働くわけです。ただし、テーブル名のような文字列は型でつながっていないので、この網にはかかりません。今回の demo_users がまさにそうでした。

4. 自動テスト ＋ CI
「ダッシュボードから AI チャットを呼ぶと答えが返る」というテストがあれば、demo_users を消した時点でテストが失敗します。それを CI（Cloud Build）でマージ前に自動で実行すれば、壊れたコードは main に入れません。

現場では、これがいちばん頼りにされている網です。人の注意力に頼らず、毎回必ず動くからです。

5. コードレビュー
PR を出すと、チームメイトが変更内容を見ます。chat.py を書いた本人なら「それ消すとチャットが壊れるよ」とすぐ気づけます。「誰がどのファイルの担当か」を決めて、その人に自動でレビュー依頼が飛ぶ仕組み（GitHub の CODEOWNERS）もあります。

6. ログ・監視
それでもすり抜けたものは、本番のエラーログや通知で見つけます。最後の網ですが、ここで見つかったときには、もう利用者に迷惑がかかっています。
